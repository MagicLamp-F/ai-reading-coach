# 项目章程

## 1. 为什么做

本项目的核心目标不是做一个普通书籍推荐机器人，而是构建一个“以推荐和反馈为交互探针的个人用户建模系统”。

书籍推荐只是稳定的提问方式。真正目标是通过每日推荐、按钮反馈、原因反馈和周期性反思，长期沉淀一个多维、可解释、可复盘的个人用户模型，让用户更了解自己：

- 长期真正关注什么问题。
- 短期正在被什么牵引。
- 哪些知识缺口阻碍行动。
- 偏好什么样的信息表达和学习路径。
- 反感什么类型的信息、主题或叙述方式。
- 当前处于研究、搭建、验证还是扩展阶段。
- 哪些反复出现的问题构成更深层的自我叙事。

核心定义：

```text
推荐 = 系统提出一个关于用户的假设
反馈 = 用户验证、修正或推翻这个假设
画像更新 = 把反馈解释成多维用户模型变化
复盘 = 帮助用户理解自己
```

## 2. 做成什么样

第一阶段目标是个人 MVP：

- 部署在腾讯云国内轻量服务器。
- 模型和搜索优先使用国内可访问 API。
- 飞书作为第一交互入口。
- 每天固定时间推送 3 本书。
- 每本书都带有系统假设、推荐理由、对应画像维度和可能不适合的原因。
- 用户通过飞书消息卡片或反馈链接完成按钮反馈。
- 关键反馈后追加原因选择。
- 反馈进入 SQLite，保留可审计证据。
- Hermes 周期性读取事实记录，更新长期记忆摘要和用户画像解释。
- 每 7 天生成一次用户画像复盘。

目标体验：

```text
系统不是简单问“你喜欢这本书吗？”
而是在说：
我推荐这本书，是因为我假设你现在真正缺的是 X。
请通过反馈告诉我这个假设是否成立。
```

## 3. 为什么这样做

纯按钮反馈不足以建立深层用户模型，但它低摩擦，适合启动闭环。

完全依赖 Agent 自然记忆也不够可靠，因为它难以保证：

- 原始证据可追溯。
- 画像变化可解释。
- 推荐失败可复盘。
- 成本和调用次数可控制。
- 定时任务和消息回调可稳定执行。

飞书优先是当前最适合国内部署的选择：

- 国内服务器访问飞书和国内 API 更稳定。
- 飞书卡片适合“推荐 + 按钮反馈 + 原因选择”。
- 后续可以从自定义机器人升级到飞书应用机器人。
- 不需要先处理 Telegram 在国内服务器上的网络问题。

因此采用分层架构：

```text
飞书负责交互体验
SQLite 负责事实记忆
Hermes 负责长期理解和反思
Python 后端负责可靠编排
OpenClaw 后续负责 Gateway 和 Skill 执行
Skill 负责沉淀行为规范
```

## 4. 项目边界

第一阶段做：

- 单用户个人 MVP。
- 飞书作为主要交互入口。
- SQLite 作为事实数据库。
- Python 后端作为编排和稳定性层。
- Hermes 作为长期记忆和反思层的接入目标。
- OpenClaw 作为后续 Gateway/Skill 执行层接入目标。
- 每日推荐、按钮反馈、原因反馈、7 天复盘。

第一阶段不做：

- 多用户账号系统。
- 商业化后台。
- 支付。
- 复杂 Web 前端。
- 自动购买书籍。
- 个人微信非官方机器人。
- 在国内服务器上依赖不稳定代理连接 Telegram。
- 自动改代码或自动修改策略后直接上线。

## 5. 成功标准

7 天成功标准：

- 每天稳定生成 3 本推荐。
- 每本推荐都能说明系统假设。
- 飞书能收到推荐消息。
- 反馈能写入数据库。
- 画像能基于反馈变化。
- 7 天复盘能指出至少 3 条用户认为准确的观察。
- 复盘能指出至少 1 条系统误解。

30 天成功标准：

- 能看出长期兴趣和短期关注的变化。
- 能区分兴趣、知识缺口、时机不匹配和表达偏好。
- 用户模型明显优于初始用户说明书。
- 推荐不只是变准，而是能帮助用户发现自己反复关注的问题。
