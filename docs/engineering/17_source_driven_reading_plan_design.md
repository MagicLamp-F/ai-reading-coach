# 书源驱动阅读计划与每日伴读包需求评估

日期：2026-06-02

## 一句话判断

这个需求值得做，但不要定义成“AI 替用户读书”。更合适的定义是：

```text
用户提供确定要读的书源
-> 系统按读几天或每天读多少分钟生成阅读计划
-> 每天切出待读内容
-> 基于当天原文生成伴读快读包
-> 用户阅读、反馈、沉淀
```

它的核心价值不是总结一本书，而是把“我想读这本书”转化成“今天具体读哪一段、怎么读、读完留下什么”。

## 需求描述

用户可以把书源上传或登记到服务器，包括但不限于：

- PDF
- EPUB
- Markdown / TXT
- 网页文章合集
- 用户手动整理的章节摘录
- 已授权的电子书文本

用户为一本书设置阅读计划：

- 计划读几天，例如 7 天读完；
- 或每天读多少分钟，例如每天 30 分钟；
- 或同时设置两者，由系统在章节长度、文本密度和用户时间之间做平衡。

系统每天生成：

- 今日待读文件或阅读片段；
- 今日快读包；
- 读前主线提示；
- 关键概念、论证链和例子；
- 和用户画像、当前问题、长期目标有关的连接；
- 读后反馈入口。

## 这个需求有什么用

### 1. 把推荐系统升级成阅读执行系统

当前系统已经可以推荐书、生成快读包、收集反馈。这个需求会把链路往前推进一步：

```text
推荐一本书
-> 用户选择要读
-> 系统生成阅读计划
-> 每天陪用户读
-> 反馈进入画像
-> 下次推荐更准确
```

这会让系统从“推荐器”变成“读书私教”。

### 2. 降低开始读书的摩擦

很多书不是因为不值得读而被搁置，而是因为每天不知道从哪里开始、读多少、读完怎么处理。每日待读片段可以把一本大书变成一个可执行任务：

```text
今天只读这一段
今天只回答这几个问题
今天只沉淀这几个要点
```

这对长期坚持比一次性总结更有价值。

### 3. 让快读包有真实书源 grounding

当前快读包主要依赖推荐上下文、公开网页来源、Hermes 模型知识和少量 source excerpt。用户提供完整或半完整书源后，系统可以直接基于当天原文生成内容，质量会更稳定。

这能改善几个问题：

- 不再只依赖营销页、书评页或搜索摘要；
- 可以引用章节结构和具体段落；
- 可以区分“原文明确说了什么”和“模型推断了什么”；
- 可以减少 hallucination。

### 4. 帮助用户形成读后沉淀

每日伴读包不只做摘要，还可以生成：

- 今日最重要的 3 个观点；
- 今日最值得怀疑的 1 个观点；
- 和用户当前项目相关的应用题；
- 可写入长期记忆的用户偏好变化；
- 下次阅读需要追踪的问题。

这些反馈可以进入 `feedback_events`、`profile_items`、`reading_packs`、后续 reflection 和周报。

### 5. 形成个人书库与阅读历史

每本书可以沉淀为：

- 原始书源；
- 阅读计划；
- 每日阅读片段；
- 每日快读包；
- 用户反馈；
- 最终全书复盘；
- 和用户画像有关的长期记忆。

这会让 `library/` 不只是推荐 artifact，而是个人阅读资产库。

## 优势

### 1. 和“自己看书”关联更强

如果设计成伴读模式，AI 不替用户读完，而是帮助用户更好地读原文。它增强的是阅读执行、理解和沉淀，不是替代阅读体验。

### 2. 适合当前系统演进

当前系统已经具备这些基础：

- SQLite 事实层；
- reading pack 生成；
- artifact 保存；
- 飞书提醒；
- ARC 阅读页；
- 用户反馈；
- Hermes 生成；
- source collector 雏形。

新增书源计划模块是顺着已有架构扩展，而不是另起炉灶。

### 3. 可以提高推荐后的转化

推荐系统的常见问题是“推荐完就结束”。这个需求可以让用户对推荐结果做一个明确动作：

```text
加入阅读计划
跳过
只看快读包
以后再读
```

这些动作本身就是高价值反馈。

### 4. 更容易验证效果

这个需求可以用清晰指标验证：

- 一本书是否按计划读完；
- 每日是否打开阅读页；
- 用户是否看了原文；
- 用户是否提交反馈；
- 读后是否产生长期记忆变化；
- 下次推荐是否更贴近。

相比“摘要质量好不好”，这些指标更接近真实使用价值。

### 5. 能支持不同阅读深度

同一本书可以有不同模式：

- 速览：只看 10 分钟快读包；
- 伴读：每天读原文 + 快读包；
- 深读：每日问题、摘录、复盘、应用题；
- 复习：只看历史快读包和自己的反馈。

这让系统可以适配不同书和不同状态。

## 劣势与风险

### 1. 书源处理复杂

PDF、EPUB、网页、Markdown 的解析难度不同。尤其 PDF 可能有：

- 页眉页脚干扰；
- 目录和正文混杂；
- 扫描版 OCR 问题；
- 脚注、图表、公式；
- 多栏排版；
- 章节识别困难。

如果第一版试图支持所有格式，会很容易拖慢。

### 2. 版权与权限边界必须明确

系统只能处理用户合法提供且有权个人阅读的书源。不要做公开抓取受保护全文、绕过付费墙、批量分发书籍内容等能力。

工程上也要避免把完整书源通过飞书或公开 URL 暴露出去。阅读页需要签名 URL、访问控制和过期机制。

### 3. 可能诱导用户只看摘要

如果产品默认把“快读包”放得太突出，用户可能逐渐不读原文，只消费 AI 二手内容。这会削弱读书私教的目标。

因此默认体验应该是：

```text
原文片段是主体
快读包是辅助
反馈和沉淀是闭环
```

### 4. 小说类作品容易被伤害体验

长篇小说、文学作品和叙事性强的书，价值不只是信息密度。过度总结会破坏：

- 悬念；
- 节奏；
- 人物情绪；
- 语言风格；
- 审美体验；
- 伏笔揭示。

所以小说不适合默认“代读总结”，更适合“无剧透伴读”和“已读章节复盘”。

### 5. 成本可能升高

如果每天把大量原文、历史上下文、用户画像和长输出 schema 一起送给模型，成本会很高。需要限制：

- 每日输入字符数；
- 原文 chunk 大小；
- 每日模型调用次数；
- 是否生成深度包；
- 是否压缩来源；
- 是否缓存中间结果。

### 6. 计划切分不一定等于认知切分

按字数或页数平均切书很简单，但不一定符合阅读体验。一本书中有些章节很密，有些章节很轻。系统需要逐步支持：

- 章节边界；
- 小节边界；
- 文本密度；
- 概念密度；
- 用户预计阅读速度；
- 用户反馈后的动态调整。

第一版可以先保守切分，后续再优化。

## 和用户自己看书的关系

这个需求和“自己看书”的关系可以分三档。

### 强关联：伴读

用户仍然读原文，AI 帮忙规划、提示、提问、复盘。

适合：

- 非虚构；
- 商业书；
- 管理书；
- 心理学；
- 技术书；
- 历史/社科；
- 需要应用到现实问题的书。

这是最推荐的方向。

### 中关联：读前预习和读后复盘

用户主要靠自己读，AI 只在读前给主线，读后帮忙整理。

适合：

- 信息量较高但用户希望保留自主阅读体验的书；
- 小说；
- 传记；
- 文学评论；
- 哲学类文本。

### 弱关联：代读摘要

用户不读原文，只看 AI 总结。

适合：

- 快速判断一本书值不值得读；
- 对低优先级书做扫读；
- 为选书做比较；
- 已读过后快速回忆。

不建议作为默认主路径。

## 是否只适合长篇小说总结

不是。

这个需求对长篇小说“总结着看”的价值反而不是最高。小说如果只总结，会损失阅读体验。它对非虚构和知识型书籍的价值更稳定，因为这些书通常可以拆成：

- 概念；
- 论点；
- 论证；
- 案例；
- 方法；
- 反例；
- 应用场景。

小说可以支持，但要换模式：

- 不剧透今日阅读提示；
- 已读章节摘要；
- 人物关系更新；
- 伏笔记录但不提前揭示；
- 主题和叙事结构复盘；
- 读完后全书分析。

所以结论是：

```text
非虚构：适合做伴读和快读包。
长篇小说：适合做无剧透伴读和已读复盘，不适合默认代读。
```

## 推荐的 MVP 收敛

第一版不要做全格式、全自动、全书深度解析。建议只做“书源驱动的每日伴读 MVP”。

### MVP 输入

- 手动上传或放置 Markdown / TXT 书源；
- 可选支持 EPUB；
- 暂不优先支持复杂 PDF；
- 一本书一个 source directory。

### MVP 配置

每本书支持：

```text
book_id
title
author
source_path
plan_days
daily_minutes
start_date
mode: guided_reading | fast_read_only | review
spoiler_policy: allow | avoid
```

`plan_days` 和 `daily_minutes` 可以二选一；如果都填，系统按两者平衡，必要时提示计划过紧或过松。

### MVP 输出

每天生成：

```text
library/YYYY/MM/<book>/day-01/source.md
library/YYYY/MM/<book>/day-01/reading-pack.md
```

阅读包包含：

- 今日范围；
- 读前主线；
- 关键观点；
- 关键例子；
- 今日问题；
- 和用户有关的连接；
- 读后反馈入口；
- 明确标注哪些内容来自原文，哪些是模型推断。

### MVP 数据表方向

可以新增或扩展：

```text
book_sources
reading_plans
reading_plan_days
reading_day_packs
reading_progress_events
```

其中：

- `book_sources` 保存书源元数据；
- `reading_plans` 保存一本书的计划；
- `reading_plan_days` 保存每日切片；
- `reading_day_packs` 保存每日伴读包；
- `reading_progress_events` 保存打开、完成、反馈、调整计划等事件。

## 产品原则

1. 原文优先，快读包辅助。
2. 用户决定读哪本书，系统负责降低执行成本。
3. 不把来源不足的内容伪装成深度理解。
4. 小说默认不剧透。
5. 完整书源不通过飞书公开发送。
6. 先支持高质量少量书源，再扩展格式和自动化。
7. 每日计划可以调整，不要把计划做成僵硬任务。

## 建议优先级

### P0：需求验证

先选 1 本非虚构书，手动整理为 Markdown 或 TXT，验证：

- 系统能否切成 3-7 天；
- 每日伴读包是否真的促进阅读；
- 用户是否愿意读原文；
- 反馈是否能帮助调整后续计划。

### P1：工程实现

实现：

- 书源登记；
- 阅读计划创建；
- 每日切片；
- 每日阅读包生成；
- ARC 阅读页展示；
- 反馈写入。

### P2：格式扩展

再支持：

- EPUB 解析；
- PDF 解析；
- OCR；
- 章节自动识别；
- 阅读速度估算；
- 动态改计划。

## 最终建议

做这个需求，但把第一版严格收敛为：

```text
非虚构书源
+ 用户阅读计划
+ 每日原文切片
+ 每日伴读快读包
+ 反馈闭环
```

不要第一版就做“任意书源上传 + 自动全书拆解 + 深度总结 + 小说代读”。那会同时碰到格式解析、版权边界、模型成本和产品价值不清的问题。

这个需求真正的战略意义是：让 AI 读书私教从“每天推荐 3 本书”进入“陪用户把一本书读完”的阶段。
